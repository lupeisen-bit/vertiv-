# 任务规格：UL 标准深度页（中文 PPT 内容 JSON）

背景：为“800V DC AI 数据中心电源系统”编写 UL 标准深度解读页。用户要求每个标准“十几页起步”，且“详细介绍每个标准的重要的点并引用章节”。
你负责若干个标准，为每个标准写一个 JSON 文件到 /tmp/deck/<key>.json。主程序会把 JSON 渲染成 16:9 幻灯片。

## 事实纪律（最重要）
- 绝不编造条款号、数值、限值、试验参数。每个事实必须来自：(a) /tmp/src 下的资料文件；(b) 你自己用 WebSearch 查到的公开页面（WebSearch 结果会把长页面写入文件，可读取）。
- 每一行必须带“依据”标签：`原文`（资料中直接看到该条款文字/数值，并给出条款号）、`目录`（仅依据目录标题/Scope 页）、`解读`（你的工程解读，不带具体条款号或明确写“条款号待核对”）。
- 数值不确定就写“数值以正式文本为准”，不要猜。版本/年份以资料中看到的为准。
- /tmp/src 下文件是网页/PDF 预览文字，可能含乱码和断行；用 Grep/Read 定位（例如 grep 条款号）。你至少要读完与你标准相关的文件的关键部分，并额外做 ≥6 次 WebSearch 补充（试验参数、限值、与 800V DC 相关的限制、认证流程、IEC 对应）。
- 800V DC 相关判断：只能在“资料明确写了电压范围/限值”时下结论；否则写“需向 UL 确认”。UL 2026 年路线图资料在 /tmp/src/CurrentOS_UL_800VDC_roadmap.txt 与 /tmp/src/UL_emerging_risks_AI_datacenters.txt。
- 语言：中文，标准名、条款号、术语保留英文。不用 emoji。

## 每个标准的页数与结构
每个标准至少 10 页（资料充分的做到 12–13 页）。资料确实不足（例如 UL 2877/2140/2755 这类 OOI 没有公开目录）可少于 10 页，但不得少于 6 页，也不得灌水；你要在最终回复中说明原因。推荐结构：
1. cards：概览（版本与发布日期、Scope 要点、IEC 对应、认证对象、与 800V 的关系、证书类型）
2. table：范围与排除项（逐条 Scope 条款 1.x）
3. table_full：章节结构总览（目录：章 → 内容 → 对 800V 电源系统的相关度）
4–8. table：章节详解（5–6 页，每页聚焦一组章节，行里写具体要求、数值、判据）
9. table：试验/验证项矩阵（条款、试验、判据或参数、样品/注意）
10. cards 或 table：800V DC 适配分析（哪些条款在 800V 下更严/不覆盖/需确认）
11. cards：设计检查清单（≥12 项，可分 3 个 card）
12. cards：取证流程、样品准备、常见失败原因与应对
13. table：来源与核实状态（关键事实 → 来源文件名或 URL → 依据等级）
一个文件里若负责多个标准，请写多个 JSON 文件（每标准一个）。

## JSON 格式
{
  "key": "ul1012",
  "id": "UL 1012",
  "name_zh": "非 Class 2 电源单元",
  "edition": "第 8 版（2010-11-09，含至 2014-05-14 修订）",
  "tag": "电源",               // 页眉右上角小标签，≤6 个汉字
  "slides": [ ... ]
}
slide 两种以上 kind：

1) "table"（左表右卡，推荐）
{
  "kind": "table",
  "title": "UL 1012 §35 间距（1/2）",       // ≤30 字
  "subtitle": "…",                           // ≤40 字，可省略
  "head": ["条款", "要点", "依据"],
  "colw": [1.4, 5.6, 0.8],                   // 相对列宽
  "rows": [["§35.1.1", "…", "原文"], ...],  // 每页 ≤7 行；“要点”列 ≤75 个汉字（含数字符号），条款列 ≤14 字符
  "impact": ["…", "…"],                      // 右上卡片“对 800V 设计的影响”，≤4 条，每条 ≤48 字；可省略
  "advice": ["…"],                           // 右下卡片“取证 / 设计建议”，≤4 条，每条 ≤48 字；可省略
  "impact_title": "可选自定义标题", "advice_title": "可选自定义标题",
  "src": "来源简述（文件名/URL）", "conf": "A"   // A=条款号/数值在公开文本中核对到；B=来自二手资料/需复核
}
2) "table_full"（整页宽表，无侧卡）：同上但没有 impact/advice，colw 总宽 12.65 英寸比例，每页 ≤9 行，“要点”列 ≤90 字。
3) "cards"（2–4 张卡片）
{
  "kind": "cards", "title": "…", "subtitle": "…",
  "cards": [ {"title": "…", "color": "teal|orange|red|green", "items": ["…", ...]} ],   // 每卡 ≤6 条，每条 ≤60 字
  "src": "…", "conf": "A"
}
所有字符串里不要包含换行，不要用 Markdown。表格“依据”列只能是 原文/目录/解读 三者之一。

## 质量要求
- 每页要有实质内容：具体条款号 + 具体要求/数值/判据，而不是只复述标题。目录页之外，尽量每页 ≥60% 的行是“原文”或“目录+具体说明”。
- 章节详解页按条款顺序/主题分组，页标题注明分页（如“（2/5）”）。
- 写完后用 python3 -c "import json;json.load(open('/tmp/deck/<key>.json'))" 校验 JSON 合法，并检查：行数、字数上限、依据列取值。
- 最终回复（给主程序）≤200 字：列出写出的文件、每个标准的页数、哪些标准资料不足及原因、你认为置信度最低的 3 处。
